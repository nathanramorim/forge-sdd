# Discovery 53 — Esteira de Execução de Feature em 3 Sessões (Spec → Act → Revisor)

Esta descoberta responde a uma pergunta direta do usuário — "já implementamos usar multi-sessão aqui?" — e à direção que ele deu em seguida: para executar uma feature, a esteira deveria ter três estações separadas, **Spec**, **Act** e **Revisor**, cada uma potencialmente isolada em sua própria sessão. Investigação nesta mesma conversa confirmou que hoje isso **não existe como mecanismo operacional** — só como conceito documentado e desatualizado (`docs/metodologia-sdd.md` §9) e como uma decisão explicitamente adiada (`feat-5ae2-06`, o spike de subagentes nativos, concluiu "não migrar sem levar a decisão ao usuário" e recomendou reexecutar a investigação a cada discovery futuro — este é esse discovery).

## 1. Contexto e Problema (Porquê)

- **Hoje, Spec/Act/Revisor são "personas simuladas num único chat"** — termo usado no próprio spike `feat-5ae2-06`. O Orquestrador, dentro da mesma sessão/thread, assume mentalmente os três papéis em sequência. Não há isolamento de contexto: o Revisor "lê" o código já sabendo tudo que o Builder debateu para chegar até ali, o que é exatamente o oposto do que uma revisão de código busca (um segundo par de olhos sem o viés de quem escreveu).
- **O protocolo de paralelismo existente (`docs/metodologia-sdd.md` §9) resolve um eixo diferente do que o usuário pediu.** Ele descreve rodar **duas features inteiras** em sessões separadas ("uma feature por sessão, nunca duas no mesmo turno") — paralelismo *entre features*. O pedido do usuário é sobre paralelismo/isolamento *entre estágios de uma mesma feature* (Spec, Act, Revisor como estações distintas). São problemas relacionados mas não idênticos — este discovery trata do segundo, e propõe como os dois eixos se combinam (esteira por estágio × múltiplas features rodando a esteira ao mesmo tempo).
- **O handoff formal entre sessões já existe, mas só num nível genérico.** `sdd/FLOW.md` (Protocolo de Handoff) já declara uma linha "Sessão → Sessão: resumo do estado atual e bloqueios → `progress.md` (Handoff Context)" — usada hoje para continuar trabalho entre dias/turnos, não para delegar formalmente de Spec para Act ou de Act para Revisor dentro da mesma execução de feature. É a peça que já existe e precisa ser especializada por estágio, não inventada do zero.
- **Existem primitivos técnicos novos, não avaliados no spike anterior.** `feat-5ae2-06` avaliou apenas subagentes *dentro da mesma sessão* (`.claude/agents/*.md`, Task/Agent tool). Esta sessão tem acesso a uma camada adicional — sessões Claude Code Remote de verdade (`create_session`, `send_message`/`SendMessage`, `list_sessions`, `create_trigger`) — que permite instanciar sessões **top-level separadas**, cada uma com seu próprio ciclo de vida, mensageável e monitorável de fora. Isso muda o espaço de opções em relação ao que o spike concluiu.

## 2. Para Quem

- **O mantenedor solo do Forge-SDD** (o próprio usuário) — hoje acumula, numa única conversa longa, o contexto de especificar, implementar e revisar a mesma feature; perde o benefício de uma revisão com "olhos frescos" e paga o custo de manter tudo isso na mesma janela de contexto.
- **Quem roda várias features ao mesmo tempo** — hoje limitado pelo protocolo de paralelismo (nunca duas features no mesmo turno); uma esteira com estações isoladas abre caminho para várias features avançando concorrentemente, cada uma em sua própria tripla Spec/Act/Revisor.
- **Usuários de Gemini/Copilot** — precisam ficar cientes de que qualquer ganho de isolamento real de sessão hoje só é automatizável no Claude Code (via Claude Code Remote); nos outros dois agentes, "sessão separada" significa abrir manualmente um novo chat, sem orquestração automática.

## 3. Lacunas Identificadas

1. **Nenhuma definição formal das 3 estações como unidades de sessão.** `/nova-feature`, `/proxima-feature` e `/revisar` existem como comandos, mas nada nos hoje instrui a tratá-los como fronteiras de sessão — o Orquestrador pode (e normalmente faz) executar os três na mesma conversa.
2. **Handoff formal existe só em nível genérico** (`progress.md` Handoff Context), sem um contrato específico do que Spec deve deixar pronto para Act, e do que Act deve deixar pronto para Revisor, além do que já está implícito no arquivo de especificação e no diff de código.
3. **Paridade entre agentes não resolvida.** Só o Claude Code tem hoje primitivos maduros para isolar contexto entre estações (subagentes in-session, ou sessões Claude Code Remote separadas). Gemini e Copilot não têm equivalente automatizável — qualquer desenho da esteira precisa declarar explicitamente o que acontece nesses dois agentes (degradar para o modelo atual de personas simuladas, documentado como tal, em vez de fingir paridade que não existe).
4. **Telemetria por sessão não está desenhada para 3 sessões por feature.** O schema atual (`sdd/.metrics/schema.json`) grava um `session-<ISO8601>.json` por sessão, com `agent_path` como lista dos papéis percorridos **dentro** daquela sessão (ex.: `["orquestrador", "builder", "revisor"]`). Se Spec/Act/Revisor viram 3 sessões reais, isso vira 3 arquivos de telemetria — hoje não há campo que os amarre como pertencentes à mesma execução de feature.
5. **Regra 15 da Constituição (branch única por pasta de feature) não foi testada contra sessões múltiplas.** A regra já garante uma única branch por feature/subpasta — o que é compatível com 3 sessões trabalhando na mesma branch em sequência, mas isso nunca foi validado explicitamente como parte do desenho.

## 4. Oportunidades de Evolução (Como, macro)

- **Formalizar a esteira Spec → Act → Revisor como 3 estações sequenciais**, cada uma correspondendo a um comando já existente (`/nova-feature`, `/proxima-feature`, `/revisar`), sem inventar comandos novos — apenas declarando que cada um *pode* rodar em sessão isolada, com um contrato de handoff explícito de entrada/saída.
- **Especializar o handoff genérico já existente** (`progress.md` Handoff Context) em 3 handoffs específicos: Spec→Act (o que a especificação entrega: arquivo `feat-XX.md`/`fix-XX.md`, branch já criada, critérios de aceitação), Act→Revisor (o que a implementação entrega: lista de arquivos alterados, comandos de teste rodados, pontos de atenção — hoje já mencionado em `sdd/FLOW.md` mas sem um formato estruturado).
- **Distinguir dois mecanismos de isolamento no Claude, com trade-offs diferentes:** (a) subagentes in-session (`.claude/agents/*.md`, Task tool) — mais leve, mesma sessão top-level, bom para isolamento de contexto sem overhead operacional; (b) sessões Claude Code Remote separadas (`create_session`/`send_message`) — isolamento real entre sessões top-level, permite paralelismo genuíno entre features, mas exige orquestração explícita (quem cria a próxima sessão, quem monitora, o que acontece se uma trava).
- **Declarar explicitamente o comportamento em Gemini/Copilot** como "personas simuladas num único chat, sem isolamento real" — mantendo paridade de *resultado* (a feature ainda passa por especificação, implementação e revisão) sem fingir paridade de *mecanismo*.
- **Amarrar telemetria de múltiplas sessões à mesma feature** — campo novo (ex.: `run_id` ou reaproveitar o `feature` já existente como chave de agrupamento) permitindo que `/status`/`/doctor` reconstruam a esteira completa de uma feature a partir de 2-3 arquivos `session-*.json` separados.
- **Habilitar paralelismo real entre features** como consequência natural de estações isoladas — se cada estação é uma sessão independente, várias features podem estar simultaneamente em estações diferentes (uma em Act, outra em Revisor) sem violar "uma feature por sessão, nunca duas no mesmo turno" do protocolo antigo, porque agora "sessão" é por *estação*, não por feature inteira.

## 5. Riscos e Trade-offs

- **Overhead de reconstrução de contexto.** Cada nova sessão começa "fria" — o ganho de isolamento (revisão sem viés) tem custo direto (Act precisa reler a spec do zero; Revisor precisa reler o diff do zero). Sem um handoff bem desenhado, isso pode ser pior que a sessão única atual.
- **Paridade entre agentes é o maior risco de produto**, já identificado no spike anterior: uma esteira que só funciona de verdade no Claude Code (via Claude Code Remote ou subagentes) e degrada para simulação nos outros dois quebra a promessa de comportamento equivalente entre agentes que o Forge-SDD sustenta hoje. Decisão de produto, não só técnica — precisa ser explícita, não implícita.
- **Orquestração de sessões separadas é responsabilidade nova.** Sessões Claude Code Remote não se auto-coordenam — alguém (Orquestrador, ou o próprio usuário) precisa decidir quando criar a próxima sessão da esteira, o que fazer se uma trava ou falha, e como consolidar telemetria espalhada em múltiplos arquivos.
- **Regra 15 e branch única por feature seguem válidas**, mas o desenho precisa deixar explícito que as 3 estações operam na *mesma* branch em sequência — nunca uma branch por estação — para não recriar o problema que a Regra 15 já resolveu para subtarefas.

**Handoff:** Próximo passo (`/split-features`) deve quebrar as oportunidades acima em features dentro de `sdd/features/feat-53-multi-sessao-esteira-feature/`, priorizando primeiro o handoff estruturado Spec→Act→Revisor (menor risco, não depende de mecanismo de sessão específico) e só depois a automação de sessão real (subagentes ou Claude Code Remote), que é onde a decisão de paridade entre agentes precisa ser validada explicitamente com o usuário antes de codar.
