# Discovery 03 — Confirmação de Subagente, Comando Claude Quebrado (`.prompt`), `/status` sem Sincronização e Clarify Ausente

Esta descoberta nasce de quatro atritos concretos relatados pelo mantenedor durante sessões reais de uso: (1) o agente nunca pergunta se a próxima atividade deveria ser delegada a um subagente antes de simplesmente executá-la; (2) ao usar Claude, o comando que o próprio handoff/documentação recomenda digitar (`/nova-feature`, `/status`, etc.) **não existe** — só existe `/nova-feature.prompt`, obrigando o usuário a completar a extensão manualmente toda vez; (3) `/status` relata o estado local sem checar o remoto, então uma branch adiantada, uma publicação (PR) já aberta ou um `index.md`/`progress.md` desatualizado em relação ao GitHub passam despercebidos — como aconteceu nesta mesma sessão com a branch `claude/agent-folder-rename-forge-ww8abl`, encontrada só porque o usuário pediu investigação manual; (4) `/nova-feature`, `/novo-fix` e `/discovery` nunca têm um passo de **clarify** (esclarecer dúvidas/ambiguidades da descrição recebida antes de agir) — hoje só perguntam sobre branch de partida/retomada, nunca sobre o conteúdo em si da demanda, então descrições vagas ou incompletas seguem direto para especificação/discovery sem checagem.

## 1. Contexto e Problema (Porquê)

- **Delegação a subagente é uma decisão implícita hoje.** O ciclo `READ-MIN → PLAN → ACT → WRITE → CLOSE` de `CLAUDE.md` já obriga reportar intenção e aguardar confirmação no passo `PLAN`, mas não menciona a opção de subagente — o agente decide sozinho (ou nunca oferece) rodar a próxima etapa via `Agent`/subagente em vez de inline, mesmo em tarefas grandes (auditoria de branches, revisão multi-arquivo, pesquisa exploratória) onde isso pouparia contexto da sessão principal.
- **Confirmado nesta mesma sessão: nomeação de comando quebrada especificamente para Claude.** Inspecionando `internal/scaffold/templates/agents/claude/.claude/commands/nova-feature.prompt.md.tmpl` (e os demais 12 comandos, mesmo padrão): o arquivo se chama `<comando>.prompt.md`. A convenção de descoberta de slash command do Claude Code usa o nome do arquivo **sem a extensão `.md`** como nome do comando — então o arquivo `nova-feature.prompt.md` registra `/nova-feature.prompt`, não `/nova-feature`. Só que todo handoff gerado pelos comandos (`sdd/FLOW.md`, corpo canônico em `.agents/commands/*.md`, esta própria sessão) recomenda `/nova-feature`, `/status`, etc. — sem o sufixo. Resultado: o comando sugerido literalmente não executa por padrão, obrigando o usuário a digitar a extensão manualmente ou o comando falha silenciosamente.
- **`.gemini/prompts/*.prompt.md` e `.github/prompts/*.prompt.md` usam a mesma extensão por convenção própria de cada ferramenta** (Copilot exige `.prompt.md` para arquivos de prompt reusáveis; Gemini CLI segue o mesmo padrão de nomenclatura adotado neste repo) — ou seja, o problema é **específico do adaptador Claude**, não dos três agentes. Corrigir de forma genérica (ex: mudar só o texto do handoff) quebraria a convenção correta dos outros dois.
- **`/status` audita só `sdd/memory/progress.md` e `sdd/features/index.md` — nunca `git`/`gh`.** Confirmado nesta sessão: rodar manualmente `git fetch`, comparar `origin/main` com a branch atual, e listar PRs via `gh pr list` revelou (a) uma branch remota nova sem PR associada, criada por outra sessão de agente, contendo uma correção completa nunca integrada; (b) o PR da feature ativa em estado `draft` havia ficado parado sem menção em `progress.md`. Nenhum desses dois fatos aparece hoje no relatório de `/status`, porque o comando (`.agents/commands/status.md`) só lê arquivos locais do repositório de trabalho, nunca consulta o estado remoto.
- **Risco de conflito de índice/memória por decisão cega.** Como `/status` não verifica o remoto, é possível (e já quase aconteceu nesta sessão) que `progress.md`/`index.md` sejam editados a partir de uma leitura desatualizada — por exemplo, sugerindo `/proxima-feature` para algo que já tem PR aberto em outra branch, ou recriando uma feature que outra sessão/agente já resolveu remotamente.
- **`/nova-feature`, `/novo-fix` e `/discovery` não têm passo de clarify.** Inspecionando `.agents/commands/nova-feature.md`, `.agents/commands/novo-fix.md` e `.agents/commands/discovery.md`: os três só perguntam sobre branch de partida/retomada (`nova-feature`/`novo-fix`) ou pulam direto para a produção dos três artefatos (`discovery`). Nenhum pergunta ativamente se a descrição recebida do usuário tem lacunas, ambiguidade de escopo, critério de aceitação implícito, ou termo que precisa de confirmação antes de virar especificação/discovery formal — diferente do passo `PLAN` do lifecycle geral, que só pede confirmação da intenção já formada pelo próprio agente, não checagem de dúvida sobre o pedido original.
- **Esse gap gera dois riscos combinados.** Sem clarify, um pedido vago vira uma especificação (`feat-ID-*.md`) ou discovery inteiro construído sobre suposições não confirmadas — retrabalho só descoberto na revisão (`/revisar`) ou, pior, depois do PR. E como nem toda demanda precisa de clarify (pedidos já bem definidos não devem gerar pergunta por pergunta), a ausência de um critério explícito hoje faz o agente ou nunca perguntar, ou perguntar de forma inconsistente entre sessões.

## 2. Para Quem

- **O mantenedor do forge-sdd**, que roda sessões longas e multi-tarefa e precisa decidir explicitamente quando uma etapa vale a pena isolar em subagente (economia de contexto) em vez de descobrir isso só quando o contexto já está cheio.
- **Qualquer usuário Claude do forge-sdd** — hoje 100% dos usuários Claude são afetados pelo comando quebrado, já que o padrão vale para os 12 comandos, não um caso isolado.
- **Times com múltiplas sessões/agentes atuando no mesmo repositório** (confirmado nesta sessão: uma branch `claude/*` criada por outra sessão, sem PR, sem entrada no índice) — precisam que `/status` funcione como radar do que já foi feito remotamente antes de decidir o próximo passo.
- **Revisores/mantenedores que confiam em `progress.md`/`index.md` como fonte de verdade** — hoje esses arquivos podem divergir silenciosamente do estado real do GitHub (branches, PRs, publicações), gerando risco de retrabalho ou sobreposição.
- **Quem abre `/nova-feature`, `/novo-fix` ou `/discovery` com uma descrição curta/ambígua** — hoje não recebe nenhuma pergunta de volta antes do artefato ser gerado, mesmo quando a descrição deixa escopo, critério de aceitação ou motivação em aberto.

## 3. Lacunas Identificadas

1. **Nenhuma regra de lifecycle pergunta sobre delegação a subagente** antes de iniciar a próxima atividade/comando — decisão hoje é implícita e não auditável pelo usuário.
2. **Adaptador Claude usa extensão de arquivo incompatível com sua própria convenção de descoberta de slash command** — `<comando>.prompt.md` deveria ser `<comando>.md` especificamente na pasta `.claude/commands/` (e no template-fonte correspondente), sem alterar Gemini/Copilot.
3. **`/status` não executa nenhuma verificação de estado remoto** (`git fetch`, comparação ahead/behind com `origin/<branch>` e `origin/main`, `gh pr list`/`gh pr view` para a branch corrente) antes de reportar — não detecta branches órfãs, PRs abertos não referenciados no índice, nem divergência entre `progress.md`/`index.md` e o GitHub real.
4. **Nenhum passo formal de "sincronizar antes de decidir"** — o comando sugerido ao final de `/status` (`Próximo comando sugerido`) pode recomendar uma ação que já está obsoleta por trabalho remoto não visto localmente.
5. **`/nova-feature`, `/novo-fix` e `/discovery` não têm passo de clarify** sobre o conteúdo da demanda recebida (só perguntam sobre branch) — nem critério para decidir quando esse passo é necessário, gerando comportamento inconsistente entre sessões (às vezes pergunta, às vezes não, sem regra explícita).

## 4. Oportunidades de Evolução (Como, macro)

- **Adicionar passo de confirmação de subagente ao protocolo de lifecycle** (`CLAUDE.md`/`GEMINI.md`/chatmode Copilot, ou o corpo canônico em `.agents/commands/`, conforme escopo técnico definido em `/split-features`): antes de iniciar a próxima atividade ou comando, perguntar objetivamente ao usuário se a tarefa deve ser delegada a um subagente (com uma recomendação padrão baseada em critério simples — ex: tarefa de pesquisa/varredura extensa → sugerir subagente; edição direta e pequena → sugerir inline), deixando a decisão final com o usuário.
- **Renomear os 12 arquivos de comando do adaptador Claude** de `<comando>.prompt.md` para `<comando>.md`, tanto no repositório (`.claude/commands/*.md`) quanto na fonte de template (`internal/scaffold/templates/agents/claude/.claude/commands/*.md.tmpl`) e golden fixtures correspondentes — sem tocar nos adaptadores Gemini/Copilot, que mantêm `.prompt.md` por exigência própria de cada ferramenta. `forge-sdd update` precisa migrar projetos existentes (renomear/recriar sem perder customização, mesmo padrão de migração aditiva já usado para `.agents/`).
- **Estender `/status`** com uma etapa de sincronização/verificação remota antes do relatório: `git fetch` (ou equivalente), comparação ahead/behind da branch atual e de `main` contra `origin`, listagem de PRs abertos (`gh pr list`) e checagem se cada um está refletido em `sdd/features/index.md`/`progress.md`. Branches ou PRs "órfãos" (sem entrada correspondente no índice) devem ser reportados explicitamente como um novo item do relatório, não silenciados.
- **Novo item no relatório de `/status`:** seção "Divergência remota" — lista branches remotas novas sem feature/fix associado, PRs abertos não referenciados, e qualquer commit em `origin/main` ainda não incorporado à branch ativa — para reduzir o risco de decisões (`progress.md`/`index.md`) tomadas com base em estado desatualizado.
- **Adicionar passo de clarify a `/nova-feature`, `/novo-fix` e `/discovery`**, com critério objetivo e compartilhado (mesmo corpo canônico, evitando reescrever a regra três vezes): antes do PASSO 1 (branch) em `nova-feature`/`novo-fix`, ou antes da produção dos três artefatos em `discovery`, o agente avalia se a descrição recebida tem lacuna relevante (escopo indefinido, critério de aceitação ausente, termo ambíguo, motivação não explicada) e, só nesse caso, faz uma rodada de perguntas objetivas ao usuário antes de prosseguir. Descrições já claras e completas seguem direto, sem pergunta forçada — o clarify é condicional, não obrigatório a cada invocação.

## 5. Riscos e Trade-offs

- Perguntar sobre delegação a subagente em toda atividade pode adicionar fricção desnecessária em tarefas triviais — precisa de critério objetivo (tamanho/escopo estimado da tarefa) para não virar pergunta obrigatória e cansativa a cada passo; considerar default sensato com opção de "sempre perguntar" vs. "só perguntar acima de um limiar" configurável.
- Renomear arquivos do adaptador Claude é uma mudança de estrutura de arquivo que afeta templates, golden fixtures e qualquer projeto já scaffoldado — precisa de migração em `forge-sdd update` (aditiva, preservando customização do usuário, mesmo cuidado já usado para `.agents/rules/`/`.agents/commands/`) para não quebrar projetos existentes que já têm `.claude/commands/*.prompt.md` no disco.
- `git fetch`/`gh pr list` dentro de `/status` introduz dependência de rede e de `gh` autenticado — precisa de fallback claro (aviso, não erro fatal) quando `gh` não está instalado/autenticado ou não há acesso de rede, consistente com a regra já existente de "se VCS for `nenhum`, não tentar nenhum comando de VCS" da Constituição.
- Comparar `index.md`/`progress.md` com PRs abertos requer alguma heurística de correspondência (nome de branch ↔ entrada no índice) — precisa de regra simples e determinística (ex: prefixo de branch bate com coluna `Branch` do índice) para evitar falso-positivo/negativo.
- Critério de "quando clarify é necessário" é subjetivo por natureza — precisa de heurística objetiva o suficiente para ser consistente entre sessões (ex: lista curta de sinais: ausência de critério de aceitação, escopo com mais de uma interpretação plausível, dependência externa não mencionada) sem virar checklist rígido que interrompe pedidos já claros.
- Aplicar a mesma regra de clarify a três comandos (`/nova-feature`, `/novo-fix`, `/discovery`) exige que ela viva em um único lugar compartilhado (corpo canônico ou arquivo de referência único) para não duplicar a heurística três vezes e divergir com o tempo — mesmo princípio já usado para `naming-convention.md`.

**Handoff:** Próximo passo (`/split-features`) deve quebrar estas oportunidades em features dentro de `sdd/features/feat-03-ergonomia-de-comandos-e-sincronizacao/`, priorizando: (1) correção do nome de arquivo do adaptador Claude — menor risco, maior impacto imediato (comando hoje não funciona por padrão); (2) sincronização remota em `/status`; (3) passo de clarify em `/nova-feature`/`/novo-fix`/`/discovery`; (4) regra de confirmação de subagente no lifecycle (maior superfície, toca o protocolo usado por todo comando).
