# Discovery 02 — Fonte Única de Agente (`.agent/`) e Branch Única por Feature Quebrada

Esta descoberta parte de três dores concretas relatadas pelo mantenedor, fora do escopo da discovery-01 (que atacou lifecycle, telemetria e configuração de MCP/VCS): (1) não existe um lugar neutro para declarar regras de domínio (design system, arquitetura de frontend, acessibilidade, etc.) que qualquer agente de IA configurado no projeto (Claude, Gemini, Copilot) possa consultar sem duplicar arquivo por agente; (2) essa mesma duplicação já existe hoje, e de forma pior, na estrutura inteira de comandos — cada agente tem sua própria pasta (`.claude/`, `.gemini/`, `.github/`) com um arquivo quase-idêntico por comando, então toda mudança de comportamento exige editar 3 arquivos divergentes; (3) quando uma feature é quebrada em subtarefas dentro de uma subpasta (`sdd/features/feat-XX-nome/`), os prompts não têm regra explícita de que a pasta inteira é a unidade de execução — nem perguntam ao usuário qual branch usar como ponto de partida, ou se deve continuar uma branch de feature já iniciada. Escopo desta discovery foi expandido, a pedido do mantenedor, de "só rules" para "fonte única de agente" — resolvendo a causa raiz da duplicação, não só o sintoma de regras ausentes.

## 1. Contexto e Problema (Porquê)

- **Duplicação de comando confirmada nesta sessão, não só suspeitada.** Comparando `discovery.prompt.md.tmpl` dos três agentes: mesmo comando, mesma intenção, três textos diferentes (Claude usa "Assuma o papel de...", Gemini usa "Você deve atuar como...", Copilot usa "Você deve atuar como..." mas com frontmatter `description`/`agent` e sintaxe `${input:...}` que os outros dois não têm). Isso não é cosmético — a discovery-01 já havia identificado que esse padrão gerou pelo menos 2 correções reativas (telemetria só-Gemini, `/novo-fix` ausente no Copilot) porque uma mudança feita em um agente não se propaga automaticamente aos outros dois.
- **Sem lugar neutro para regras de domínio.** As mesmas três árvores de configuração por agente (`internal/scaffold/templates/agents/claude/.claude`, `agents/gemini/.gemini`, `agents/openai/.openai`) também não têm convenção para regras de projeto reutilizáveis (ex: "componentes seguem o design system X", "toda tela nova precisa de rota acessível"). Hoje isso, quando existe, fica solto em `CLAUDE.md`/`GEMINI.md` ou na cabeça do usuário.
- **Cada agente exige sua própria pasta por restrição de ferramenta, não por escolha de design.** Claude descobre comandos em `.claude/commands/`, Gemini em `.gemini/prompts/`, Copilot em `.github/prompts/` (com frontmatter próprio). Essas três pastas não podem ser eliminadas — são o mecanismo de descoberta de cada ferramenta. O que pode ser eliminado é o **conteúdo duplicado dentro delas**: hoje cada uma carrega o corpo inteiro da instrução; poderiam carregar só o essencial de formato/invocação da ferramenta e apontar para um corpo único e compartilhado.
- **`forge-sdd update` hoje preserva domínio (feat-31) mas não conhece uma fonte única de agente.** O fluxo de upgrade já tem o cuidado de não sobrescrever `sdd/features/`, `sdd/discovery/`, `sdd/fix/*` e `progress.md` (estado do projeto). Introduzir uma nova convenção de fonte única sem estender esse fluxo de migração deixaria projetos existentes travados na estrutura antiga (3 pastas divergentes) sem caminho de atualização.
- **Branch por subtask, não por feature.** Investigação nesta sessão em `.claude/commands/proxima-feature.prompt.md` confirma: o passo 1 faz `git checkout -b <branch>` usando o campo **Branch** do arquivo de feature/tarefa individual — mas quando uma feature é quebrada em subpastas (`sdd/features/feat-XX-nome/feat-XX-01-*.md`, `feat-XX-02-*.md`, ...; ver `feat-01-simplificacao-e-aprendizado-continuo/`), os arquivos de subtarefa não declaram um campo Branch próprio, e não há instrução explícita dizendo que a subpasta inteira deve virar uma única branch. O comportamento hoje depende de o modelo inferir isso corretamente — igual ao problema de telemetria probabilística já corrigido na discovery-01 (feat-01-01).
- **Nenhuma pergunta sobre branch de partida.** Os prompts assumem implicitamente a branch atual do checkout como ponto de partida. Não há pergunta ao usuário sobre (a) partir de `main` ou de outra branch, nem (b) continuar uma branch de feature já criada anteriormente (cenário comum quando uma sessão anterior parou no meio de uma feature quebrada em várias subtarefas).

## 2. Para Quem

- **Mantenedores/times que usam mais de um agente de IA no mesmo projeto** (Claude, Gemini, Copilot) — hoje não têm como declarar "esse comportamento vale para qualquer um desses agentes" sem editar/copiar arquivo em 3 lugares, tanto para regras quanto para comandos.
- **O próprio mantenedor do forge-sdd**, que autora e mantém os templates em `internal/scaffold/templates/` — paga hoje o custo direto de 3 arquivos por comando (confirmado: ~36 arquivos para 12 comandos), com risco real de divergência a cada mudança.
- **Projetos com identidade visual/arquitetural própria** (design system, guidelines de acessibilidade, convenções de frontend) que hoje não têm onde registrar isso de forma que reduza contexto carregado pelo agente a cada tarefa.
- **Usuários que já rodam `forge-sdd update`** em projetos existentes e esperam ganhar a nova estrutura sem perder o estado atual (features/discoveries/fixes e o "ponto" em que o projeto está).
- **Times que quebram features grandes em subpastas** (`sdd/features/feat-XX-nome/`) — hoje sem clareza de estratégia de branch, arriscando N branches para uma única entrega coesa, ou perdendo trabalho em progresso por não retomar a branch certa.

## 3. Lacunas Identificadas

1. **Nenhuma fonte única de comportamento de agente** — comandos e regras existem só como cópias divergentes por agente (`.claude/`, `.gemini/`, `.github/`), sem um corpo compartilhado do qual derivem.
2. **Nenhuma convenção `.agent/rules/*.md`** — não existe hoje pasta neutra para regras de domínio livres, consultáveis por qualquer agente.
3. **`forge-sdd update` não migra estrutura nova preservando estado** — precisa de um passo aditivo e idempotente (mesmo padrão do feat-31) que introduza a fonte única em projetos existentes sem tocar `sdd/features/`, `sdd/discovery/`, `sdd/fix/*`, `progress.md` ou a branch/ponto atual do projeto.
4. **Nenhuma regra declara a subpasta de feature quebrada como unidade de branch** — hoje o comportamento de "uma branch para a feature toda, agrupando as subtarefas" depende de inferência do modelo, não de instrução explícita nos prompts (`/nova-feature`, `/proxima-feature`, `/novo-fix`, chatmodes Orquestrador).
5. **Nenhuma pergunta obrigatória sobre branch de partida ou retomada** — os prompts não perguntam se deve partir de `main`/outra branch, nem se deve continuar uma branch de feature já existente de sessão anterior.

## 4. Oportunidades de Evolução (Como, macro)

- **Introduzir `.agent/` como fonte única na raiz do projeto**, com duas subpastas: `.agent/rules/*.md` (regras de domínio livres, definidas pelo usuário) e `.agent/commands/*.md` (corpo canônico de cada comando SDD — o texto de instrução em si, agnóstico de ferramenta). O forge-sdd escaffolda e mantém essa fonte; o conteúdo de `rules/` é do usuário, o de `commands/` é gerado pelo forge-sdd a partir de um único template por comando (não mais um por agente).
- **`.claude/`, `.gemini/`, `.github/` viram adaptadores finos, não cópias.** Cada arquivo específico de ferramenta mantém só o que é obrigatório para aquele ecossistema (frontmatter do Copilot, sintaxe de invocação de cada um) e, no corpo, instrui o agente a ler `.agent/commands/<comando>.md` para a instrução completa — mesmo mecanismo de "consulta sob demanda" que já funciona hoje para `sdd/memory/progress.md`/`lessons.md`. Isso não é possível remover fisicamente as 3 pastas (são o mecanismo de descoberta de cada ferramenta), mas elimina a duplicação de **conteúdo**: uma mudança de comportamento passa a ser editada uma vez em `.agent/commands/`, não três.
- **Regras seguem o mesmo princípio, sem adaptador necessário.** `.agent/rules/*.md` é markdown puro sem formato específico de ferramenta — os três agentes apontam para o mesmo caminho com uma única instrução curta, sem nenhuma camada intermediária.
- **Estender o fluxo de `forge-sdd update`** (mesmo ponto de extensão do feat-31 — preservação de domínio) com um passo de migração aditivo: cria `.agent/rules/` e `.agent/commands/` se ausentes; converte adaptadores existentes em `.claude/`/`.gemini/`/`.github/` para a versão fina referenciando `.agent/commands/`, preservando qualquer customização do usuário detectável (ver riscos); nunca altera `sdd/features/`, `sdd/discovery/`, `sdd/fix/*`, `progress.md`, nem a branch atual.
- **Formalizar "feature quebrada = uma branch"** como regra de lifecycle: ao detectar que a feature corrente é uma subpasta (`sdd/features/feat-XX-nome/*.md`), os prompts de execução tratam a pasta inteira como unidade, usando uma única branch (`feat/XX-nome`) que agrupa todas as subtarefas.
- **Perguntar branch de partida e retomada como passo obrigatório** antes de criar/usar a branch: (a) qual branch usar como ponto de partida (default `main`, mas configurável), e (b) se já existe uma branch de feature anterior para aquela mesma pasta (`git branch --list feat/XX-*`) que deve ser retomada em vez de recriada.

## 5. Riscos e Trade-offs

- **Migrar comandos existentes para adaptador fino é mais arriscado que criar `.agent/rules/` do zero.** Projetos já rodando podem ter customizado o conteúdo de um comando dentro de `.claude/commands/` diretamente. A migração via `update` precisa detectar edição manual (ex: diff contra o template original conhecido) e, se detectada, **não sobrescrever** — deixar o adaptador antigo como está e avisar o usuário, em vez de forçar a conversão. Mesmo espírito de "não sobrescrever" já declarado como decisão resolvida da Constituição.
- Convenção "consultar por referência" depende de cada agente de fato ler arquivos sob demanda — os três já fazem isso hoje com `sdd/memory/progress.md`/`lessons.md`, então o padrão é o mesmo, mas precisa validação nos três (Claude/Gemini/Copilot) para não regredir, incluindo o caso de comandos (não só regras).
- Migração via `forge-sdd update` precisa ser estritamente aditiva/idempotente — reexecuções não podem duplicar conteúdo nem sobrescrever regra/comando já editado pelo usuário (mesmo cuidado do feat-31, testável com golden fixtures).
- Mudar a estratégia de branch para "uma por pasta de feature" é uma mudança de comportamento default de `/nova-feature`/`/proxima-feature` — precisa preservar o caminho hoje testado para features de arquivo único (sem subpasta), que continuam com uma branch por arquivo como já funciona.
- Perguntar branch de partida a cada execução adiciona uma interação — mitigar com default sensato (`main`) que só exige resposta explícita quando há ambiguidade real (branch de feature anterior detectada).
- Pedido do usuário é publicar como `v2.2.0-beta`, pulando `2.1.0-beta` (versão atual em `sdd/.sddrc`/`internal/config/config.go` é `2.0.0-beta`) — decisão explícita do usuário, registrada aqui para não ser tratada como erro de versionamento em revisão futura.

**Handoff:** Próximo passo (`/split-features`) deve quebrar estas oportunidades em features dentro de `sdd/features/feat-02-agent-rules-e-branch-por-feature/`, priorizando: (1) `.agent/rules/` — menor risco, sem migração de conteúdo existente; (2) `.agent/commands/` + adaptadores finos para os três agentes; (3) migração em `forge-sdd update` (rules primeiro, depois commands, dado o risco de customização detectado); (4) regra de lifecycle de branch única por pasta de feature (maior impacto de comportamento, exige mais validação).
