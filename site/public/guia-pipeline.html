Três sessões trabalhando juntas. Você só decide.

Conversa e decide numa sessão enquanto outras duas constroem e revisam sozinhas. Este guia mostra como abrir, usar e acompanhar tudo, do zero.

A ideia

Antes, um agente só concebia, construía e revisava o próprio código. Agora cada papel tem a sua sessão, e elas conversam por uma fila local.

vocêforge-discoverySessão interativa: você conversa, refina a feature, aprova a spec e dispara a construção.
workerforge-builderPega o job da fila, constrói (em paralelo o que for independente), roda os testes e abre o PR.
workerforge-reviewerConfere o PR contra spec, ADRs e rules. Devolve com feedback ou aprova e avisa você.
O pipeline nunca mescla nada.Quem aprova e mescla o PR é você. As duas sessões de trabalho só entregam o PR revisado.

Começar

1Instalar

npm install -g @nathanramorim/forge-sdd@beta
# o "@beta" é importante: a versão estável (latest) ainda não tem o pipeline

2Abrir o menu

Na pasta do seu projeto, rode:

forge

Setas navegam, Enter escolhe, Esc volta. Num projeto sem Forge, a primeira opção é Instalar.

3Iniciar as 3 sessões

Em Pipeline multi-sessão → Iniciar as 3 sessões o menu pergunta:

  • Qual agente roda em cada sessão (Claude, Gemini, Copilot ou Codex). Pode misturar. A última escolha já vem marcada.
  • O nível de permissão dos workers (veja a seção Agentes).
  • Mostra a checagem (CLI instalada? arquivos do agente no projeto?) e pede confirmação.

Se for a primeira vez, o menu oferece ativar o pipeline (cria .forge/config/forge.json). Depois de confirmar, as três sessões abrem.

Prefere sem menu? 
forge-sdd pipeline init
forge-sdd up --discovery claude --builder codex --reviewer gemini

Fluxo de uma feature

Do pedido ao PR pronto. Você só atua nas caixas azuis.

você · discoveryDescreve a demanda/discovery gera spec e critérios
→
você · discoveryAprova o Gate 1e roda /split-features
→
automáticoEntrega ao Buildero split já roda o dispatch (gate + job)
forge-builderConstróitestes, lint, abre o PR
→
forge-reviewerConfere o PRspec, ADRs, rules
→
se não conformeDevolve ao Builderaté 3 vezes, com feedback
→
você · discoveryRecebe o avisoPR pronto no inbox; você aprova
A Discovery não constrói.Em modo pipeline, quem constrói é o Builder. Se a Discovery tentar rodar queue next ou queue complete, o Forge recusa (a menos que você use --local, por sua conta).

Agentes e permissões

Cada sessão pode usar um agente diferente. Estes são os oferecidos:

geminiGEMINI.mdgemini -p

Antes de abrir, o menu confere se a CLI está instalada. Se faltar o arquivo de instruções, ele avisa e indica forge-sdd update --agent <nome> (para o Codex, o agente se chama openai).

Permissões dos workers

O Builder e o Reviewer rodam sem você aprovar cada passo. Por isso há dois níveis:

project (padrão)Edita arquivos e roda só os comandos de allow_commands (git, gh, forge-sdd). Para rodar testes do seu projeto, acrescente (go, npm…) em .forge/config/forge.json.
fullSem pedir confirmação nenhuma (o bypass de cada CLI). Use só em ambiente isolado.

No Gemini, o nível project libera só edição: para o Builder rodar testes com Gemini, é preciso full.

Painéis e contingência do tmux

Com o tmux instalado, as três sessões abrem numa tela só: Discovery grande à esquerda; Builder e Reviewer empilhados à direita, cada painel com o nome da sessão no topo. Sem tmux, o Forge oferece contingência suave com instalação assistida ou janelas nativas.

Instalação assistida e contingência suaveSe o tmux não estiver instalado, em modo auto o Forge detecta o gerenciador de pacotes (Homebrew no macOS; apt-get, dnf, pacman, apk ou zypper no Linux) e pergunta se você deseja instalá-lo automaticamente. Se recusar ou a instalação falhar, o Forge cai com graça (contingência do tmux) para janelas nativas do sistema (ou três painéis no Windows Terminal wt.exe no Windows). No WSL, o tmux roda nativamente na distribuição Linux.

Quando o agente bate o limite de uso

Se o agente avisa que acabou a cota (como o limite de 5 horas do Claude), o worker não falha o job:

  • O job volta à fila sem gastar tentativa, e o painel mostra ⏸ limite de uso do claude: retomo às 22:40.
  • O inbox da Discovery recebe um aviso.
  • O worker espera e retoma sozinho (até 6 horas; no máximo 3 devoluções por job).
  • Limite semanal ou com data (resets Nov 20) faz o job falhar com o motivo, para não ficar preso.

Toda falha agora traz a última linha útil do agente, não só "código 1".

Se algo não anda

SintomaO que fazer
Painel do Builder "Aguardando jobs" e nada aconteceConfira a fila: forge-sdd bus list --role builder. Sem job, rode /split-features ou /implementar <feature> na Discovery.
/implementar bloqueadoLeia a lista de pendências: falta card, ADR, rule ou a evidência do card. Sem gerenciador de projeto, desligue a exigência do card (veja "Fluxo").
Job parado em processing (worker caiu)15 minutos depois: forge-sdd bus recover --role builder (ou reviewer).
Quero devolver um job à filaforge-sdd bus requeue --role builder --id <job> --worker <sessão>
Erro dizendo que a CLI não está no PATHInstale a CLI do agente escolhido ou escolha outro no menu. O menu mostra "(não encontrado no PATH)".
Linhas "hook … failed: ECONNREFUSED"Vêm de um hook global seu (~/.claude/settings.json), não do Forge; o worker as resume em uma linha.
Quero voltar ao fluxo de uma sessão sóApague .forge/config/forge.json ou use a Estrutura padrão no menu.

O guia completo também fica em cada projeto, em .forge/LEIA-ME.md.

Limites desta beta

  • Gemini, Copilot e Codex seguem a documentação oficial das CLIs, mas ainda não rodaram de ponta a ponta com o worker.
  • O forge.json que você já tinha mantém os argumentos antigos dos perfis; a visão limpa cai no acompanhamento por git até você atualizar cli_profiles (ou rodar pipeline init num projeto novo).
  • O tmux foi testado na versão 3.8 (macOS), sem o attach num terminal real.
  • A proteção "a Discovery não constrói" é uma barreira de processo, não de segurança.
