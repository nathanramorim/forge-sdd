Começando com o Forge-SDD

O Forge-SDD é um orquestrador de desenvolvimento que conecta você e sua IA num fluxo de trabalho claro: você decide, a IA implementa, você aprova.

1. Instalação e setup

O forge init faz perguntas interativas sobre o projeto (nome, stack, banco). Se a sua IA faz o setup por você, use o prompt abaixo — ele coleta essas respostas antes de rodar o comando, sem travar em prompts interativos.

Para a prévia, instale com npm install -g @nathanramorim/forge-sdd@beta. O prompt abaixo instala a versão estável. Depois do forge init, rode forge doctor para conferir se tudo ficou no lugar. Já usa o forge? Veja Atualizar.

Prompt para IA 
Quero instalar o forge-sdd aqui. Me ajude a configurar.

Primeira pergunta: o que você está construindo?
Descreva com suas palavras — pode ser simples, ex:
"um app de agendamentos", "uma API para meu e-commerce", "um script que lê planilhas".

Com base no que você me contar, vou sugerir a melhor configuração
seguindo boas práticas de mercado e confirmar com você antes de rodar.

Depois da confirmação, instale assim:
npm install -g @nathanramorim/forge-sdd
forge init --yes --name "[nome]" --stack [stack] --db [db] --agent [agente]

Se preferir instalar agora com configuração padrão e ajustar depois,
responda apenas: padrão

2. Defina as regras do projeto (/constitution)

Antes da primeira feature, você precisa registrar as decisões invioláveis do projeto: qual banco usar, como nomear branches, se usa ORM ou SQL direto, qualquer escolha que a IA não deve questionar. Essas regras formam a Constitution — um arquivo que todos os agentes leem antes de trabalhar.

Sem a Constitution, a IA toma decisões arbitrárias que você vai reverter mais tarde. Com ela, cada feature nasce alinhada com o que você decidiu.

Exemplo de instrução para a Constitution:

Nunca use ORM; acesso a banco sempre via SQL direto com prepared statements.
Branches de feature seguem o padrão feat/[número]-[nome-curto].
Prompt para IA 
Vamos definir as regras do projeto com /constitution.
Execute /constitution e me ajude a cadastrar as primeiras decisões arquiteturais.
Comece me fazendo as 3 perguntas mais importantes para este tipo de projeto:
quais são as decisões que mais causam atrito se não forem definidas logo no início?

3. Primeira feature

Com o setup e a Constitution no lugar, peça à IA para criar a primeira feature. Ela roda o /discovery, escreve a spec num PR em draft, o Reviewer confere o julgamento e a IA espera o seu [Seguir] antes de escrever uma linha de código. Veja o passo a passo em Como funciona.

Prompt para IA 
Vamos criar a primeira feature com o forge-sdd.
Execute /discovery [descreva aqui o que você quer construir].
Me mostre o plano antes de implementar.

Como funciona o processo

O Forge-SDD divide o trabalho em três sessões, cada uma com uma responsabilidade: o Discovery conversa com você e escreve a spec, o Builder implementa, e o Reviewer confere. Você não precisa programar: você decide em dois pontos.

O que acontece em cada passo

  1. Spec primeiro (passos 1 a 4).

    O /discovery (ou /nova-feature e /novo-fix) escreve o que será feito e como saberemos que ficou certo. A spec vai num PR próprio, em draft. O Reviewer faz a Conferência 1: confere se o julgamento da spec está certo. Só com o seu [Seguir] a spec entra na main. É o primeiro ponto onde você decide.

  2. Uma branch e um PR draft por feature (passos 5 e 6).

    O /implementar abre uma branch por feature, sempre a partir da main, e o Builder escreve código e testes. Se o projeto tem um script de CI local (scripts/ci-local.sh), ele roda na sua máquina e grava o selo do commit: o GitHub não gasta CI enquanto o trabalho não foi conferido. Sem esse script, este passo não existe e vale só o parecer.

  3. Parecer do commit atual (passos 7 e 8).

    O Reviewer confere o PR contra a spec, as decisões do projeto (ADRs) e as regras. Se não estiver conforme, devolve ao Builder com o feedback. Se estiver, o PR sai do draft. Onde a barreira de PR está instalada (hoje, o Claude Code), o gh pr ready só passa com parecer conforme do commit atual, e com o selo do CI local quando o projeto o usa; se o código mudou depois da revisão, ele pede uma nova.

  4. CI do GitHub uma vez, e você mescla (passos 9 e 10).

    O fluxo prevê o CI do GitHub uma vez, quando o PR sai do draft (configure o seu workflow para rodar em ready_for_review). Com tudo verde, você decide o merge: é o segundo ponto onde você decide. O pipeline nunca mescla sozinho.

O que ficou mais leve

  • O fluxo guarda o CI do GitHub para o final, depois de tudo validado em casa.
  • Nenhum PR depende de outro: cada feature sai da main e volta para ela.
  • O forge doctor mostra se a barreira de PR está ligada no seu agente (ela vale no Claude Code; nos outros agentes não há barreira local, e o workflow opcional forge-pronto.yml só registra a passagem do PR para pronto).

Exemplos práticos

Veja como adicionar uma feature real do início ao fim.

Adicionar comando forge greet

Neste exemplo, vamos adicionar um comando que imprime "Olá, mundo!" no terminal.

  1. Inicie o discovery.

    Mande o prompt abaixo para sua IA:

    Prompt para IA 
    Inicie o discovery para: adicionar comando forge greet
Execute /discovery e me mostre o plano antes de implementar.
  2. Dê o [Seguir] na spec.

    A IA mostra a spec (num PR em draft) e o Reviewer confere o julgamento. Se estiver certo, responda [Seguir] no menu; a spec entra na main e só então o código começa.

  3. Acompanhe a feature até o merge.

    O Builder abre um PR em draft para a feature e o Reviewer emite o parecer. Com o parecer conforme, o PR sai do draft e o CI do GitHub roda uma vez. Você confere o diff e faz o merge.

Hub mode — um forge para vários repos

Em vez de rodar forge init em cada repo separado, você elege um repo como hub e os outros como satélites. O hub rastreia o status de todos os projetos do time em um único lugar.

Passo a passo

  1. Inicialize o repo hub.

    No repositório que será o hub central, rode:

    forge init
  2. Vincule os repos satélites.

    Para cada repo do time que você quer rastrear:

    forge init --link ../outro-repo
  3. Veja o status de todos.

    No repo hub, rode forge pipeline para ver o estado de cada repo vinculado:

    forge pipeline
Prompt para IA 
Configure o forge-sdd como hub neste workspace.
O repo atual é o hub. Para cada repo satélite, rode:
forge init --link <caminho-do-repo>
Me diga quando terminar e mostre os repos vinculados.
Prompt para IA 
Liste todos os repos vinculados ao hub e o status de cada um:
forge pipeline
Mostre quais têm features abertas e quais estão sem atividade.

Atualizar o Forge-SDD

Vale para qualquer versão nova, estável ou beta. Seus arquivos não são sobrescritos: quando algo seu conflita com o que mudou, a versão nova fica ao lado, num arquivo .novo.md, para você comparar.

  1. Instale a versão nova. 
    npm install -g @nathanramorim/forge-sdd          # estável
npm install -g @nathanramorim/forge-sdd@beta     # prévia
  2. Veja o que vai mudar, sem mexer em nada. 
    forge update --dry-run
  3. Aplique a atualização.

    Rode no seu terminal, fora do agente.

    forge update --upgrade
  4. Reconfigure o projeto.

    No chat do seu agente, leve a estrutura, as regras e os prompts novos para o projeto:

    /upgrade-sdd
  5. Confira se ficou tudo certo. 
    forge doctor

O que esperar

  • Instruções e regras que você editou não são trocadas; a versão nova aparece como .novo.md.
  • A Constituição ganha os campos novos por acréscimo, sem apagar o que você escreveu.
  • O workflow de CI do forge é opcional e só entra se você pedir (--ci). CI próprio nunca é tocado.
  • Se algo estranho aparecer, rode forge doctor e envie a saída a quem mantém o projeto.

Recuperação: rodei o update com a 5.2.0-beta

A 5.2.0-beta antiga reescrevia arquivos de instrução e copiava o script da barreira de PR sem marcá-lo, e o forge passava a tratá-los como seus. Se o forge update avisou que manteve algum deles e você não os editou, recupere assim. Use só os arquivos que o aviso citou, e lembre que o git restore descarta alterações ainda não commitadas neles.

  1. Volte ao que estava no git os arquivos que o aviso citou.

    Por exemplo, se o aviso citou o CLAUDE.md e o GEMINI.md:

    git restore CLAUDE.md GEMINI.md

    Os nomes possíveis são CLAUDE.md, GEMINI.md, AGENTS.md, OPENAI.md, .github/copilot-instructions.md, .gemini/system_instructions.md e .openai/system_instructions.md.

  2. Apague, com confirmação, só o .novo de cada arquivo que você restaurou. 
    rm -i CLAUDE.novo.md GEMINI.novo.md

    Se o aviso citou scripts/pr_guard.py, apague também o scripts/pr_guard.py copiado à mão: com a 5.2.2-beta o forge o reconhece sozinho quando ele é idêntico a uma versão que ele entregou.

  3. Rode o update de novo e confira. 
    forge update --upgrade
forge doctor

Se você de fato editou algum desses arquivos, não restaure: compare com o .novo ao lado e junte à mão.
